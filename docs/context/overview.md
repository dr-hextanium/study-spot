# Overview and decisions

## Summary

A web app (PWA) that helps Stony Brook University students pick a study spot. It answers "where should I go right now" with a ranked recommendation, backed by a surveyed directory of every study spot on campus, historical busyness forecasts, and sparse live reports from users.

The app is a campus utility, not a business. It must be cheap to run, open source, and transferable to a student club so it survives the founder graduating.

## Status of decisions

Items marked DECIDED were confirmed by the project owner. Items marked PROPOSED came out of design discussion and are not yet confirmed; treat them as defaults that can change.

### DECIDED
- No deployed hardware of any kind (no sensors, door counters, beacons, ESP32 nodes). Not feasible.
- The directory of spots is a core product on its own, not just scaffolding for live data.
- A "pick a spot for me near a location" interaction is a core feature.
- Spot definition and attribute schema in sections 5 and 6 are accepted.
- Some Residential Computing Centers (RCCs) are believed to be residents-only. Eligibility must be modeled per spot. Verify each RCC individually.
- Language: fully typed TypeScript everywhere, strict settings ([stack.md](stack.md)).
- Validation and schemas: Zod, as the single source of truth for API types.
- Server framework: Fastify.
- Bun as the toolchain (package manager, scripts, tests) and the intended server runtime.

### PROPOSED
- Platform: web-first React + Vite PWA for v0; Expo (React Native) app added at v1 only if metrics justify it ([stack.md](stack.md)).
- Server runtime: Fastify on Bun, with code kept runtime-agnostic so Node is a drop-in fallback.
- Database: Postgres with Drizzle ORM and drizzle-zod ([stack.md](stack.md)). MongoDB considered and rejected.
- App name: Perch (decided 2026-10-10); see Naming below.
- Recommendation-first home screen, map as secondary browse mode.
- Session mode (check-in, minimal focus timer, check-out) as the main live-data hook.
- Version plan and timeline in sections 12 and 14.

## Naming (decided: Perch)

- Chosen: Perch (owner, 2026-10-10). Short, verbable ("perch me somewhere quiet"), not tied to one campus.
- Former fallback: OpenSeat. States the core promise (seat probability) literally.
- Other candidates considered: Nook, Roost, Den, Haunt, Hush, Lull, Cove, Settle.
- Rules: no "Seawolf", "SBU", or "Stony Brook" in the name (university trademarks, locks app to one campus).
- Before launch: check App Store, Play Store, and USPTO for conflicts; check domain and social handles (fallbacks like getperch or perch.study).
- The repo, packages (`@perch/*`) and deploy projects use `perch`. The old neutral placeholder `study-spot` is gone except in persisted browser storage names (see decision 21).

18. Outbox requirements handed to plan D (2026-10-04, plan B final review): the `Lock` adapter defaults to an in-process lock, and apps/web must back it with Web Locks so tabs sharing storage take turns. Dead tabs: a `syncing` record from another tab is trusted until reload today, so plan D adds an owner id on syncing records and a liveness check in `pick` and `start()`; `start()` must not reset another live tab's in-flight write. The acceptance tests are in `packages/ui-logic/test/outbox.deadtab.test.ts`, skipped until then. Note for plan D: a spot held by another tab schedules no retry timer, so liveness must be re-checked on a timer, not only on foreground, online, or enqueue. A 5xx, 408, or 429 holds only that spot for the rest of the pass while other spots go on (skip-spot-on-5xx); a later pass started by any trigger tries it again, so the backoff paces timer retries only. Plan D owns a persisted server-copy cache: the spot list and spot details are persisted for offline use, merged from `onApplied`, and a stored version is never lowered. `onApplied` passes the applied write's `client_write_id` and kind (null for Keep theirs), so the UI ties "Saved" and "Marked as checked" toasts to the server's answer.
19. Surveyor web UI plan (2026-10-04, finished 2026-10-09), detail in `docs/superpowers/plans/2026-10-04-surveyor-2a-web-1-foundation.md`, its parts 2 and 3, and the redesign plan: `packages/ui-logic` gains `Liveness` and `QueueSignal` adapters; a `syncing` write carries its tab's owner id, `pick` and `start()` leave a live tab's write alone and take over a gone tab's (no owner counts as gone), a pass that skips a live tab's spot rechecks in 15 s, `settle` matches the owner, and the in-process defaults are keyed by the outbox's cache; apps/web uses a per-tab Web Lock and BroadcastChannel. `enqueue` seeds with the larger of the screen's version and the last stored server version. The server cache is TanStack Query persisted to IndexedDB (`query:survey`, survey queries only, each checked by Zod on restore, `gcTime` Infinity because 30 days overflows timers, `staleTime` 0), admin queries are never persisted, and every server spot is merged so a version never goes down. `cover_photo_id` on survey spots covers approved covers with stored bytes only, campus-scoped, and defaults to null for old caches. The server adds `GET /survey/campus` (campus time zone and buildings) and `?relogin=1` on re-login invite links; the invite screen never accepts on load. Sign-out is a mechanism only (`deps.signOut`: stop the outbox, clear the persisted survey cache and the session, keep queued writes, and remember the queue owner in `outbox:owner`); there is no sign-out UI yet. When a different surveyor accepts an invite with a non-empty queue, the app confirms after the invite is accepted and before the session is saved: Cancel keeps their changes (the link is spent), Discard runs stop, idle, `discardAll`, then join, and `resume` runs if the join fails. `resume()` restarts a stopped outbox, and `resumeOnNewSession` acts only on a token change. `noteServerVersion` adopts only an exact +1 bump (the surveyor's own unpublish or photo approval); a write already in flight is not rebased, a documented limit, because rebasing could hide a real conflict. Toasts count a write as settled only when the server applies it; "Saved on this phone" waits otherwise, and so does the walk-end message. Create and photo uploads use idempotent ids: one per submit and one per picked file. Slugs are name plus building id; a location fix counts within 50 m; a check older than 90 days reads as stale, and the "Due" filter is never checked or more than 90 days. Unpublish and photo approval are online calls. The busyness grid has time blocks as rows. Hours edit one block per day and keep further blocks. Web unit tests run under Vitest (jsdom, excluded from `bun test`), browser tests under Playwright against `apps/server/scripts/e2e-server.ts` (PGlite, fsTarget, a clock starting 2026-10-13). The look is decision 20 and visual verification lives in `CLAUDE.md`. `DESIGN.md` is written from the built screens.

22. Photo bytes off Neon (2026-10-10): Neon Free is 1 GB and every photo was stored in Postgres. Migration 0004 makes `photo_blob.bytes` nullable and adds `pages_hash` and `offloaded_at`. After each deploy, the publisher fetches each published photo from the data site, cache-busted. When the sha256 matches, it clears the Postgres bytes and keeps the row, the sha256 and the Pages asset hash. Pending photos, photos not yet confirmed, and photos shared with another campus keep their bytes. Every deploy lists the bundle's photos plus every cleared photo still used by a photo row of the campus, by stored hash and without reading bytes. A Pages deploy drops unlisted files, and a cleared photo has no other copy. A cleared hash that Cloudflare reports missing is fetched back from the live site and checked. With no good copy, the deploy stops before the deployment call. The image route fetches cleared photos from the data site and checks them. A redirect was rejected because the client sends a bearer token, and whether a cross-origin redirect drops it depends on the browser. Rejecting a photo deletes its blob when no other photo uses it. Published photo bytes now live only on the `perch-data` site and are not in the database backups (`docs/ops.md` section 10). R2 stays rejected (it needs a card).
23. Photo offload review fixes (2026-10-10). Each publish holds a database lease: `bundle_state.publishing_owner` and `publishing_until`, migration 0005, claimed with a conditional UPDATE and expiring after 10 minutes. Without it, two processes could deploy a manifest built before the other cleared a photo. Session advisory locks were rejected because they do not hold through Neon's pooler. Approved photos cannot be rejected (409), because the admin screen rejects only pending photos and an approved one may have no copy but the data site. Re-uploading a cleared blob's bytes puts them back. Upload bytes are stored inside the write transaction. `spot_photo.spot_id` is `ON DELETE RESTRICT` (migration 0006). Data-site reads stop past 25 MiB while streaming. `smoke-publish.ts` runs only against localhost. Hard rule: never roll the API back past migration 0004 (`docs/ops.md` section 8).
